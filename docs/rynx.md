# Rynx — the Ryn package manager

`rynx` is the project and dependency manager that ships with Ryn. Version 0.2
is intentionally small: it manages a manifest, installs path and git
dependencies, records a lock file, and delegates building and running to `ryn`.

```sh
rynx --version
# rynx 0.2.0 (Ryn v0.2)
# package manager for the Ryn language
```

## Quick start

```sh
mkdir demo
cd demo
rynx init demo
rynx run
```

`rynx init` creates:

```
demo/
  rynx.toml
  src/main.ryn
```

Add a dependency from a sibling directory or a git repository:

```sh
rynx add ../greet
rynx add https://github.com/example/utils.git --tag v1.0.0 --name utils
rynx install
rynx list
```

## Commands

| Command | Description |
| --- | --- |
| `rynx init [name]` | Create `rynx.toml` and `src/main.ryn` in the current directory. The name defaults to the directory name. |
| `rynx add <path>` | Add a path dependency, validate its manifest, and install it. |
| `rynx add <url>` | Add a git dependency and clone it into `.rynx/packages`. `https://`, `http://`, `ssh://`, `git://` and `git@` URLs are detected automatically; `--git` forces git mode. |
| `rynx remove <name>` | Remove a dependency from the manifest, delete its installed directory, and refresh the lock file. |
| `rynx install` | Resolve every dependency, clone missing git dependencies, validate path dependencies, and write `rynx.lock`. |
| `rynx list` | Print the package name, version, entry point, and dependencies. |
| `rynx build [args...]` | Run `ryn build <entry>` with the given extra arguments. |
| `rynx run [args...]` | Run `ryn run <entry>` with the given extra arguments. Program arguments can follow `--`. |
| `rynx clean` | Delete `.rynx` (installed dependencies). The manifest and lock file are kept. |
| `rynx version`, `rynx --version`, `rynx -V` | Print the rynx and Ryn versions. |
| `rynx help`, `rynx --help`, `rynx -h` | Print usage. |

Options for `rynx add`:

| Option | Description |
| --- | --- |
| `--name <name>` | Use a different dependency name. |
| `--git` | Force the argument to be treated as a git URL. |
| `--tag <ref>` | Clone a specific git tag. |
| `--branch <ref>` | Clone a specific git branch. |
| `--rev <ref>` | Alias for a specific revision; currently passed as a git branch/tag. |

## Manifest format

`rynx.toml` uses a deliberately small TOML subset: sections, quoted strings,
comments, and single-line inline tables. Numbers, arrays, booleans,
multi-line strings and nested tables are not supported.

```toml
# rynx.toml
[package]
name = "demo"
version = "0.2.0"
entry = "src/main.ryn"

[dependencies]
greet = "../greet"
utils = { git = "https://github.com/example/utils.git", tag = "v1.0.0" }
helper = { path = "../helper" }
```

- `name` must be lowercase letters, digits, `_` or `-`, starting with a letter
  or `_`.
- `version` is required and is currently a free-form string.
- `entry` defaults to `src/main.ryn`.
- A dependency is either a quoted path (shorthand for `{ path = "..." }`) or an
  inline table with exactly one of `path` or `git`.
- Git dependencies accept `tag`, `branch` or `rev`; at most one may be given.
  `rynx` passes the value to `git clone --branch`, so tags and branches work;
  arbitrary commit hashes are not resolved yet.
- Every dependency directory must contain its own `rynx.toml` with a package
  name and version.

`rynx add` rewrites `rynx.toml` in a canonical form, so comments and custom
formatting in the `[dependencies]` table are not preserved. Hand-written
manifests are fine as long as they follow the subset above.

## Installed layout

```
.rynx/
  packages/
    utils/          # git clone, with its own rynx.toml
rynx.lock
```

Path dependencies are not copied; the lock records the path and the version
read from the dependency's manifest, and the compiler resolves imports through
that manifest. Git dependencies are cloned into
`.rynx/packages/<name>`. Existing clones are reused by `install`; delete
`.rynx` or the package directory (or run `rynx clean`) to force a fresh clone.

`rynx.lock` is written after every `install`, `add` and `remove`:

```toml
# Generated by rynx. Do not edit.
version = 1

[[package]]
name = "utils"
source = "git"
git = "https://github.com/example/utils.git"
ref = "v1.0.0"
version = "1.0.0"
```

The lock is currently informational: `install` re-resolves dependencies instead
of reading exact pinned revisions from it. Commit it to record what was
installed, but do not rely on it for reproducible offline installs yet.

## Compiler integration

Ryn 0.2 resolves `import <name>` to user modules and packages. `rynx build` and
`rynx run` pass the project's `.rynx/packages` directory to the compiler with
`--module-path`; a dependency installed there can be imported directly:

```ryn
# src/main.ryn
import greet

fn main() -> i32:
    println(greet.greeting())
    return 0
```

Git dependencies are cloned into `.rynx/packages/<name>`. `path` dependencies
are not copied; the compiler reads the `[dependencies]` table from the manifest
closest to the importing file and maps each `path` dependency name to its
directory. A package exposes a module from, in order:

```
src/lib.ryn
src/<package>.ryn
src/mod.ryn
<package>.ryn
lib.ryn
mod.ryn
entry from rynx.toml
```

The package entry point is still used by `rynx build` and `rynx run`, so a
dependency remains a complete standalone Ryn project. See
[modules.md](modules.md) for the full resolution order, visibility rules, and
how module names are qualified.

## Toolchain discovery

`rynx build` and `rynx run` find the compiler in this order:

1. `$RYN`, if set;
2. a `ryn`/`ryn.exe` next to the `rynx` executable;
3. `ryn` on `PATH`.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success |
| `1` | Manifest, dependency, installation or I/O error |
| `2` | Usage error |
| `3` | The `ryn` compiler could not be started |

`rynx run` and `rynx build` propagate the exit status of the compiler (and, for
`run`, of the program itself).

## Limitations

- No central registry, publishing, semantic-version solving, or dependency
  graph upgrades yet.
- No checksum verification; git dependencies rely on git's transport security.
- No transitive dependency installation: only dependencies listed in the root
  manifest are installed.
- The lock file is written but not consumed.
- Git dependencies require a `git` executable and network access.
- Linux, macOS and Windows builds are exercised through CI; Windows uses the
  same path and process helpers as the compiler.
